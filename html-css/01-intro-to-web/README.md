## 1. Інтернет і WWW — не одне й те саме

| Поняття | Що це |
|---|---|
| **Інтернет** | Фізична й логічна інфраструктура мереж, що працює на стеку протоколів **TCP/IP**. «Дороги». |
| **World Wide Web (WWW)** | Один із сервісів поверх Інтернету: система документів і ресурсів, пов'язаних **гіперпосиланнями** та **URL**. «Магазини вздовж доріг». |

Інші сервіси Інтернету, що **не є** вебом: електронна пошта (SMTP/IMAP), FTP, DNS, WebSocket, SSH тощо.

### Коротка історія

- **1989–1991** — Тім Бернерс-Лі (CERN) пропонує концепцію вебу.
- **1990** — разом із Робертом Кайо створено **HTTP**, систему адресації **URI** та мову **HTML**.
- **20 грудня 1990** — запрацював перший сайт: [info.cern.ch](https://info.cern.ch/) (він працює й досі!).
- **30 квітня 1993** — CERN оголошує технологію WWW безкоштовною і відкритою для всіх.

### Три «кити» вебу

1. **URI/URL** — унікальна адреса ресурсу (`https://example.com/products/123`).
2. **HTTP** — протокол обміну ресурсами.
3. **HTML** — формат документа з гіперпосиланнями.

> 💡 **Ключова інновація** — саме гіперпосилання: документ перестає бути ізольованим файлом і стає вузлом глобального графа.

## 2. URI, URL, URN та анатомія адреси

**URI** (Uniform Resource Identifier, RFC 3986) — будь-який рядок, що ідентифікує ресурс. Має два підтипи:

| Тип | Ідентифікує за… | Приклад | Що «каже» |
|---|---|---|---|
| **URL** (Locator) | місцезнаходженням | `https://example.com/books/978-3-16-148410-0.pdf` | «ресурс лежить ось тут» |
| **URN** (Name) | іменем | `urn:isbn:978-3-16-148410-0` | «це книга з таким ISBN», але не каже, де її взяти |

> **RFC** (Request for Comments) — пронумерований офіційний документ, що визначає стандарти та протоколи Інтернету.

### Анатомія URL

```
https://user:pass@www.chnu.edu.ua:443/faculty/news/index.html?page=2&sort=date#comments
└─┬─┘   └───┬───┘ └──────┬──────┘└┬┘└──────────┬───────────┘└────────┬───────┘└───┬───┘
scheme  userinfo        host    port          path                 query       fragment
        └──────────── authority ──────────┘
```

| Частина | Пояснення |
|---|---|
| **Scheme** | Спосіб доступу до ресурсу: `http`, `https`, `ftp`, `file`, `mailto`, `tel`, `ws`, `wss`. Схема ≠ «протокол HTTP». |
| **Authority** | `[userinfo@]host[:port]` |
| **Domain name** | `chnu.edu.ua`: `.ua` — домен верхнього рівня (TLD), `edu` — другого рівня, `chnu` — третього рівня (піддомен). |
| **Port** | Мережевий порт сервера. За замовчуванням: `80` для HTTP, `443` для HTTPS — тому зазвичай його не пишуть. |
| **Path** | Який ресурс/маршрут запитується. У SPA чи API це може бути просто «маршрут», а не файл. |
| **Query (parameters)** | Пари `ключ=значення`, розділені `&`. Додаткові дані для сервера. |
| **Fragment (anchor)** | Частина `#...` — **не передається серверу**. Використовується браузером (прокрутка до `id`) або JavaScript (hash-routing: `https://example.com/#/users`). |

**HTTP vs HTTPS:** HTTPS — це той самий HTTP, але поверх зашифрованого **TLS**-з'єднання (Transport Layer Security). TLS забезпечує конфіденційність (ніхто не підгляне), цілісність (ніхто не змінить дані дорогою) і автентичність (сервер — справді той, за кого себе видає, це підтверджує сертифікат).

## 3. DNS: телефонна книга інтернету

Комп'ютери спілкуються за **IP-адресами** (`195.178.19.94`), а людям зручніше пам'ятати імена (`chnu.edu.ua`). **DNS** (Domain Name System) зіставляє одне з іншим — як контакти в телефоні зіставляють ім'я і номер.

### Як працює DNS-запит

1. Ви вводите `chnu.edu.ua` в адресний рядок.
2. Браузер (а потім ОС) перевіряє **локальний DNS-кеш**. Знайшли — одразу йдемо на сервер.
3. Не знайшли — комп'ютер питає **DNS-сервер** (зазвичай провайдера або публічний, напр. `1.1.1.1`, `8.8.8.8`).
4. Отримавши IP, комп'ютер встановлює з'єднання з сервером.

### Що відбувається, коли ви натискаєте Enter (аналогія з магазином 🛒)

| Крок | Технічно | Аналогія |
|---|---|---|
| 1 | Браузер дізнається IP через DNS | Знаходите адресу магазину |
| 2 | Встановлюється TCP-з'єднання (+ TLS для HTTPS) | Їдете дорогою до магазину |
| 3 | Браузер надсилає HTTP-запит `GET /` | Робите замовлення |
| 4 | Сервер відповідає `200 OK` і надсилає файли пакетами | Магазин видає товар |
| 5 | Браузер збирає пакети й рендерить сторінку | Розпаковуєте покупки вдома |

> 🧪 **Спробуйте самі:** у терміналі виконайте `nslookup chnu.edu.ua` (Windows/Linux/macOS) — побачите IP-адресу сайту.

## 4. Клієнт-серверна архітектура та протокол HTTP

**Архітектура** — опис системи на найвищому рівні: як модулі взаємодіють між собою, без деталей реалізації.

**Клієнт-серверна архітектура** — клієнт (frontend, браузер) надсилає **запити** (request), сервер (backend) повертає **відповіді** (response).

### Учасники HTTP-обміну

- **Клієнт (user agent)** — програма, що діє від імені користувача (браузер).
- **Сервер** — програма, що приймає й обробляє запити (nginx, Apache, Node.js/Express).
- **Проксі** — посередник між ними. Може кешувати, фільтрувати (антивірус, батьківський контроль), балансувати навантаження, автентифікувати, логувати, виявляти атаки (DDoS).

### Ключові властивості HTTP

- Протокол **прикладного рівня** моделі OSI; працює поверх TCP.
- **Не зберігає стан (stateless):** кожен запит незалежний. Для «пам'яті» між запитами використовують **сесії** та **cookie** (наприклад, щоб не логінитись на кожній сторінці).
- Сервер займає **пасивну** позицію — лише відповідає на запити.

### Формат HTTP-повідомлення

```http
GET /api/users/1 HTTP/1.1           ← стартовий рядок: Метод URI Версія
Host: example.com                   ← заголовки (headers)
Accept: application/json
                                    ← порожній рядок
                                    ← тіло (body) — для GET зазвичай порожнє
```

```http
HTTP/1.1 200 OK                     ← стартовий рядок: Версія Код Статус
Content-Type: application/json
Content-Length: 42

{"id": 1, "name": "Taras Shevchenko"} ← тіло відповіді
```

**Типи вмісту тіла (Content-Type):** `text/html`, `application/json`, `multipart/form-data` та ін.

**Групи заголовків:** загальні, заголовки запиту, заголовки відповіді, заголовки сутності.

### HTTP-методи

| Метод | Дія | Приклад |
|---|---|---|
| `GET` | Отримати ресурс | `GET /api/users/1` |
| `POST` | Створити новий ресурс | `POST /api/users` |
| `PUT` | Повністю замінити ресурс | `PUT /api/users/1` |
| `PATCH` | Частково змінити ресурс | `PATCH /api/users/1` |
| `DELETE` | Видалити ресурс | `DELETE /api/users/1` |

### Коди стану (Status Codes)

| Клас | Значення | Приклади |
|---|---|---|
| **1xx** | Обробка триває | `101 Switching Protocols` |
| **2xx** | Успіх | `200 OK`, `201 Created`, `204 No Content` |
| **3xx** | Перенаправлення | `301 Moved Permanently`, `304 Not Modified`, `307 Temporary Redirect` |
| **4xx** | Помилка клієнта | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` |
| **5xx** | Помилка сервера | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` |

> 😺 Запам'ятати коди весело допоможе сайт [http.cat](https://http.cat/).

> 🧪 **Спробуйте самі:** відкрийте DevTools (`F12`) → вкладка **Network** → оновіть сторінку. Клацніть на будь-який запит і подивіться метод, статус, заголовки та тіло відповіді.

## 5. REST, AJAX, JSON: як змінювались вебзастосунки

### REST

**REST** (Representational State Transfer) — стиль побудови API, де дія визначається **HTTP-методом**, а ресурс — **адресою**:

```
POST   /api/users      → створити користувача
GET    /api/users/1    → отримати користувача з id=1
PATCH  /api/users/1    → змінити його дані
DELETE /api/users/1    → видалити
```

### Еволюція вебзастосунків

| Епоха | Як працювало |
|---|---|
| **Web 1.0** (90-ті) | Уся логіка на сервері. Будь-яка дія (навіть сортування таблиці) = **повне перезавантаження** сторінки. |
| **Web 2.0 + AJAX** (2000-ні) | **AJAX** (Asynchronous JavaScript and XML) — обмін із сервером **без перезавантаження**. Сервер повертає готовий шматок HTML, клієнт вставляє його в сторінку. |
| **Сучасні SPA/SSR** | Клієнт і сервер обмінюються **лише даними** (найчастіше **JSON**). Розмітку будує клієнт (React, Vue, Angular) або сервер (SSR — Server-Side Rendering). |

**Переваги обміну «лише даними»:** сервер і клієнт незалежні один від одного; менше трафіку; простіша серверна логіка.

**JSON** (JavaScript Object Notation) — легкий текстовий формат даних, зрозумілий і людині, і машині:

```json
{
  "id": 1,
  "name": "Леся Українка",
  "courses": ["HTML", "CSS"],
  "active": true
}
```

У браузері запити надсилають через вбудований метод `fetch()`:

```js
fetch('/api/users/1')
  .then(response => response.json())
  .then(user => console.log(user.name));
```

## 6. Стандарти W3C та WHATWG

**W3C** (World Wide Web Consortium) — заснований у **1994** р. Тімом Бернерсом-Лі для узгодження стандартів між виробниками браузерів.

| Рік | Подія |
|---|---|
| 1991 | HTML 1.0 (~20 тегів) |
| 1996 | CSS1 — відокремлення стилю від структури |
| 1997 | ECMAScript 1 — стандарт JavaScript |
| 2008–2014 | HTML5 — семантика, `<canvas>`, `<video>`, робота без плагінів (Flash) |
| 2015+ | ES6 (класи, модулі, стрілкові функції, `let/const`) та щорічні редакції ECMAScript; CSS3 модульно (Flexbox, Grid, Custom Properties) |

Після HTML5 специфікація стала **«живим стандартом» (Living Standard)**: її розвиває **WHATWG** разом із W3C безперервно, без великих нумерованих версій. Фічі додаються поступово, щойно їх реалізують браузери.

## 7. Frontend vs Backend

| | **Frontend (Client-Side)** | **Backend (Server-Side)** |
|---|---|---|
| Де виконується | У браузері користувача | На сервері |
| Відповідає за | Відображення даних, інтерфейс, взаємодію | Зберігання та обробку даних, бізнес-логіку, безпеку |
| Технології | HTML, CSS, JavaScript, фреймворки (React, Vue, Angular) | C#, Java, Python, Node.js, PHP, Go; БД (PostgreSQL, MySQL, MongoDB); API |

- **Роль клієнта для сервера** — повідомити, що робити з даними.
- **Роль клієнта для користувача** — показати дані зручно та дати змогу їх змінювати.
- **Роль сервера** — зберігати дані в **БД**, обробляти їх за правилами (**бізнес-логіка**), виконувати фонові задачі (індексація, розсилки).

## 8. Quirks Mode vs Standards Mode

Режим рендерингу визначається **наявністю `<!DOCTYPE html>`** на першому рядку документа.

| Режим | Коли вмикається | Поведінка |
|---|---|---|
| **Quirks Mode** | Немає DOCTYPE або він застарілий | Імітує браузери 1990-х: нестандартна box model, непередбачувані відмінності між браузерами |
| **Standards Mode** | `<!DOCTYPE html>` | Точна відповідність специфікаціям |

> ⚠️ **Правило №1 верстальника:** кожен HTML-документ починається з `<!DOCTYPE html>`. Перевірити режим можна в консолі: `document.compatMode` → `"CSS1Compat"` (Standards) або `"BackCompat"` (Quirks).

## 9. Critical Rendering Path

Шлях від коду до пікселів на екрані:

```
HTML ──► DOM ─┐
              ├──► Render Tree ──► Layout ──► Paint ──► Composite ──► 🖥️
CSS ──► CSSOM ┘
```

| Етап | Що відбувається |
|---|---|
| **DOM** | Парсинг HTML → дерево об'єктів документа (Document Object Model) |
| **CSSOM** | Парсинг CSS → CSS Object Model |
| **Render Tree** | Об'єднання DOM + CSSOM, **лише видимі** вузли (`display: none` сюди не потрапляє) |
| **Layout (reflow)** | Обчислення точних розмірів і координат кожного елемента |
| **Paint (repaint)** | Растеризація: заливка пікселів (кольори, тексти, тіні) по шарах |
| **Composite** | Накладання шарів і вивід на екран (часто на GPU) |

### Чому це важливо для продуктивності?

Чим «раніше» в конвеєрі етап, який зачіпає зміна, тим вона дорожча:

| Зміна властивості | Які етапи перераховуються | Вартість |
|---|---|---|
| `width`, `height`, `top`, `margin`, `font-size` | Layout → Paint → Composite | 💸💸💸 дорого |
| `color`, `background`, `box-shadow` | Paint → Composite | 💸💸 середньо |
| `transform`, `opacity` | лише Composite | 💸 дешево |

Саме тому анімації рекомендують робити через `transform` та `opacity`, а не через `left`/`top`/`width`.

## 10. Стек HTML + CSS + JS

| Технологія | Роль | Аналогія | Тип |
|---|---|---|---|
| **HTML** | Структура, семантика | Скелет 🦴 | Декларативна («що є») |
| **CSS** | Представлення, стиль | Шкіра, одяг 👕 | Декларативна («як виглядає») |
| **JavaScript** | Поведінка, інтерактивність | М'язи, мозок 🧠 | Імперативна («що робити») |

Наш курс фокусується на шарі **HTML/CSS** — статичній верстці та адаптивному дизайні.

```html
<!DOCTYPE html>
<html lang="uk">
<head>
  <meta charset="UTF-8">
  <title>Три шари</title>
  <style>
    .btn { background: royalblue; color: white; padding: 8px 16px; } /* CSS */
  </style>
</head>
<body>
  <button class="btn">Натисни мене</button>                         <!-- HTML -->
  <script>
    document.querySelector('.btn')
      .addEventListener('click', () => alert('Привіт!'));            // JS
  </script>
</body>
</html>
```

## 11. Браузерні рушії та кросбраузерність

| Рушій рендерингу | Браузери | JS-рушій |
|---|---|---|
| **Blink** | Chrome, Edge, Opera, Brave | V8 |
| **Gecko** | Firefox | SpiderMonkey |
| **WebKit** | Safari (macOS/iOS) | JavaScriptCore |

**Кросбраузерність** — проблема, коли однаковий код виглядає чи поводиться по-різному в різних браузерах, бо рушії з різною швидкістю впроваджують стандарти й по-різному їх трактують.

**Як боротися:**

- [caniuse.com](https://caniuse.com/) — перевірка підтримки властивості;
- **Progressive Enhancement** — базовий функціонал працює всюди, розширений — де підтримується;
- **Normalize.css / CSS Reset** — уніфікація «заводських» стилів браузерів;
- **BrowserStack / Playwright** — тестування в реальних браузерах.

> 🍏 **Порада:** Safari традиційно повільніше впроваджує нові CSS-фічі. Навіть якщо все «працює в Chrome», перевіряйте в Safari окремо. А всі браузери на iOS — це WebKit під капотом.

> 🤖 **Головна теза:** ШІ прискорює написання коду, але **не замінює розуміння** рендерингу, box model, каскаду CSS. Хто не розуміє, *чому* браузер зробив саме так, не зможе ні ефективно поставити задачу ШІ, ні виправити те, що воно згенерувало неправильно.

## Глосарій

| Термін | Коротко |
|---|---|
| WWW | Система гіпертекстових документів поверх Інтернету |
| URL / URI / URN | Адреса / ідентифікатор / ім'я ресурсу |

| HTTP / HTTPS | Протокол обміну ресурсами / те саме через TLS |
| TCP/IP | Базові протоколи передачі даних мережею |
| REST | Стиль API: метод + адреса ресурсу |
| AJAX | Обмін із сервером без перезавантаження сторінки |
| JSON | Текстовий формат обміну даними |
| DOM / CSSOM | Деревоподібні моделі HTML-документа та стилів |
| Reflow / Repaint | Перерахунок геометрії / перемальовування пікселів |

## Контрольні питання

1. Чим принципово відрізняється поняття «Інтернет» від поняття «World Wide Web»? Назвіть сервіси Інтернету, що не є вебом.
2. З яких трьох базових компонентів складається архітектура вебу (за Тімом Бернерсом-Лі) і яку роль виконує кожен із них?
3. Чим URI відрізняється від URL та URN? Наведіть приклад кожного.
4. Розберіть на складові URL `https://chnu.edu.ua:443/news/?page=2#top`. Яка частина не передається на сервер і чому?
5. Що таке DNS і які кроки виконуються під час DNS-запиту?
6. У чому різниця між HTTP та HTTPS? Що саме додає TLS?
7. З яких частин складається HTTP-повідомлення? Як виглядає стартовий рядок запиту та відповіді?
8. Наведіть по одному коду стану з груп 2xx, 3xx, 4xx, 5xx і поясніть їхнє призначення.
9. Які HTTP-методи використовуються в REST для створення, отримання, редагування та видалення ресурсу?
10. Що означає «HTTP не зберігає стан»? Як тоді сайт «пам'ятає», що ви авторизовані?
11. Чим відрізняється підхід AJAX від сучасного обміну даними у форматі JSON?
12. Що таке «живий стандарт» (Living Standard) і чим він відрізняється від класичного версіювання?
13. Опишіть зону відповідальності frontend- та backend-розробника. Наведіть по дві технології для кожної сторони.
14. Що вмикає `<!DOCTYPE html>` і чому без нього верстка стає непередбачуваною?
15. Перелічіть етапи Critical Rendering Path у правильному порядку.
16. Чому зміна `transform` «дешевша» для браузера, ніж зміна `width` чи `top`?
17. Що таке кросбраузерність, чим вона спричинена і які інструменти допомагають із нею боротися?
18. Чому ШІ-інструменти не замінюють розуміння фундаментальних принципів роботи браузера?

## 🎯 Міні-завдання для самоперевірки

1. Відкрийте [info.cern.ch](https://info.cern.ch/) — перший сайт в історії. Перегляньте його код (`Ctrl+U`). Чи є там DOCTYPE?
2. У DevTools → Network знайдіть запит зі статусом `301` або `304` на будь-якому популярному сайті. Поясніть, що він означає.
3. Виконайте в консолі браузера `document.compatMode` на кількох сайтах. Знайдіть сайт у Quirks Mode (підказка: дуже старі сайти).
