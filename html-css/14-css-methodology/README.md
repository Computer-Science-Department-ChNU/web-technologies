## 1. Навіщо потрібні методології

**CSS-методологія** — набір правил і домовленостей щодо **іменування класів** та **організації файлів стилів**.

### Проблеми CSS без правил 😱

- **Глобальність:** будь-який клас діє на всю сторінку → стилі одного компонента «ламають» інший.
- **Війна специфічності:** `.header .menu li a` → `#nav .menu li a` → `!important` → ...
- **Страх видаляти:** «а раптом цей клас десь ще використовується?» → CSS лише росте.
- **Неочевидні зв'язки:** з HTML не зрозуміло, які стилі де лежать.
- **Залежність від DOM:** переніс блок в інше місце — він виглядає інакше.

### Що дають методології

| Перевага                 | Пояснення                                          |
|--------------------------|----------------------------------------------------|
| 🛡 Уникнення конфліктів  | Стилі не перезаписують один одного                 |
| 📖 Читабельність         | Структура зрозуміла з назви класу                  |
| ♻️ Повторне використання | Компоненти переносяться між сторінками й проєктами |
| 📈 Масштабованість       | Нові компоненти додаються без страху щось зламати  |
| 👥 Командна робота       | Усі пишуть CSS однаково                            |

### Карта методологій

Методології відповідають на **два різні питання**:

| Як називати класи?                            | Як організувати файли й порядок стилів?        |
|-----------------------------------------------|------------------------------------------------|
| **BEM** — блоки, елементи, модифікатори       | **SMACSS** — 5 категорій стилів                |
| **OOCSS** — перевикористовувані «об'єкти»     | **ITCSS** — шари від загального до конкретного |
| **Atomic CSS** — один клас = одна властивість | нативний **`@layer`** у CSS                    |

Тому вони **не взаємовиключні** — їх поєднують. Типова комбінація: **ITCSS** для структури файлів + **BEM** для
іменування.

## 2. BEM (Block, Element, Modifier)

Найпопулярніша методологія іменування (Яндекс, ~2009). Інтерфейс ділиться на **незалежні блоки**.

### Синтаксис

```
block
block__element
block--modifier
block__element--modifier
```

Слова всередині назви пишемо через дефіс (`search-form`), `__` відділяє елемент, `--` — модифікатор. Існують інші
нотації (`block_mod`, `Block__Elem--mod`), але в курсі використовуємо лише цю.

| Сутність                   | Що це                                             | Питання, на яке відповідає назва | Приклади                                                   |
|----------------------------|---------------------------------------------------|----------------------------------|------------------------------------------------------------|
| **Block** (блок)           | Незалежний компонент, що має сенс сам по собі     | **«Що це?»**                     | `header`, `menu`, `card`, `button`, `search-form`          |
| **Element** (елемент)      | Складова частина блоку, не існує окремо від нього | **«Що це?»**                     | `menu__item`, `card__title`, `search-form__input`          |
| **Modifier** (модифікатор) | Стан, вигляд або поведінка                        | **«Який? / Як поводиться?»**     | `button--disabled`, `menu__item--active`, `card--featured` |

### Приклад

```html

<article class="card card--featured">
    <img class="card__img" src="pug.png" alt="Pug">
    <h3 class="card__title">Pug</h3>
    <p class="card__text">Шаблонізатор для HTML</p>
    <a class="card__btn button button--primary" href="#">Детальніше</a>
</article>
```

```css
.card {
    padding: 16px;
    border-radius: 12px;
}

.card--featured {
    border: 2px solid gold;
}

.card__img {
    width: 100%;
}

.card__title {
    font-size: 1.25rem;
}
```

### Правила BEM

- ✅ Назви — за **змістом**, а не за виглядом: `button--danger` ✅, `button--red` ❌, `big-block` ❌.
- ✅ Стилізуємо **лише через класи** (не теги, не id).
- ✅ Специфічність усіх селекторів однакова (0,0,1,0) → **жодних воєн специфічності**.
- ❌ **Не** відображайте вкладеність DOM у назві: `card__body__title` ❌ → `card__title` ✅. Елемент належить **блоку**, а
  не іншому елементу.
- ✅ Модифікатор **завжди йде разом** з основним класом: `class="button button--primary"`, а не лише `button--primary`.
- ✅ Блок **не задає собі** зовнішніх відступів (`margin`) і позиції — це робить батьківський блок через свій елемент.
- ✅ Один HTML-вузол може бути одночасно **елементом** одного блоку і **блоком** сам по собі (**міксування**):
  `class="card__btn button"`.

### Міксування

```css
/* блок button: як виглядає кнопка будь-де */
.button {
    padding: 8px 16px;
    border-radius: 6px;
}

.button--primary {
    background: #4b86c2;
    color: #fff;
}

/* елемент card__btn: де кнопка стоїть усередині картки */
.card__btn {
    margin-top: auto;
    align-self: flex-start;
}
```

`.button` відповідає за **вигляд**, `.card__btn` — за **положення** в конкретному батьківському блоці.

### BEM + SCSS = ❤️

```scss
.card {
    padding: 16px;

    &__title {
        font-size: 1.25rem;
    }

    &__img {
        width: 100%;
    }

    &--featured {
        border: 2px solid gold;
    }
}
```

`&__title` компілюється у **плоский** `.card__title` (а не `.card .card__title`), тому специфічність лишається 0,1,0.
Один блок = один partial-файл: `components/_card.scss`.

> ⚠️ Глибока вкладеність у SCSS (`.card { .body { h3 { … } } }`) повертає війну специфічності — уникайте її.

### 🔍 Вправа: знайдіть помилки

```html

<nav class="Menu">
    <ul class="menu__list">
        <li class="menu__list__item">
            <a class="menu__link--active" href="/">Головна</a>
        </li>
    </ul>
    <button class="menu__btn-blue big">Увійти</button>
</nav>
```

<details>
<summary>Відповідь (5 помилок)</summary>

1. `Menu` → `menu` (лише малі літери).
2. `menu__list__item` → `menu__item` (без вкладеності в назві).
3. `menu__link--active` без основного класу → `menu__link menu__link--active`.
4. `menu__btn-blue` — назва за виглядом → `menu__btn button button--primary` (міксування + модифікатор за змістом).
5. `big` — клас-вигляд без блоку → `button--large`.

</details>

| ✅ Переваги                                    | ❌ Недоліки                        |
|-----------------------------------------------|-----------------------------------|
| Ідеально для компонентного підходу            | Довгі назви класів                |
| Зрозуміла структура з першого погляду на HTML | Потрібна дисципліна команди       |
| Плоска специфічність                          | Спочатку здається «багатослівним» |
| Блоки легко переносити й видаляти             | Не регулює структуру файлів       |

## 3. OOCSS (Object-Oriented CSS)

Запропонована **Ніколь Салліван** (Nicole Sullivan, 2008). Ідея з ООП: створювати перевикористовувані CSS-**«об'єкти»**.

### Два принципи

**1. Separate structure and skin — відокремлюйте структуру від оформлення**

```css
/* ❌ Без OOCSS: усе змішано, дублювання */
.btn-login {
    padding: 8px 16px;
    border-radius: 4px;
    background: blue;
}

.btn-delete {
    padding: 8px 16px;
    border-radius: 4px;
    background: red;
}

/* ✅ OOCSS: структура окремо, «шкірки» окремо */
.btn {
    padding: 8px 16px;
    border-radius: 4px;
}

/* structure */
.skin-blue {
    background: blue;
}

/* skin */
.skin-red {
    background: red;
}
```

```html

<button class="btn skin-blue">Увійти</button>
<button class="btn skin-red">Видалити</button>
```

**2. Separate container and content — відокремлюйте вміст від контейнера**

```css
/* ❌ Залежність від місця: заголовок виглядає інакше в сайдбарі */
.sidebar h3 {
    font-size: 18px;
}

/* ✅ Об'єкт виглядає однаково будь-де */
.heading-small {
    font-size: 18px;
}
```

> 💡 Модифікатор BEM (`button--danger`) — це та сама ідея «шкірки», але зі строгим іменуванням. BEM багато що запозичив з
> OOCSS.

| ✅ Переваги                             | ❌ Недоліки                                               |
|----------------------------------------|----------------------------------------------------------|
| Гнучкі, перевикористовувані компоненти | Багато класів в HTML                                     |
| Менше дублювання CSS                   | Відсутність строгих правил іменування → «зоопарк» класів |

## 4. SMACSS

**SMACSS** (Scalable and Modular Architecture for CSS, Jonathan Snook, 2011) — ділить стилі на **5 категорій**:

| Категорія  | Що містить                           | Як стилізується               | Приклад                                  |
|------------|--------------------------------------|-------------------------------|------------------------------------------|
| **Base**   | Нормалізація, стилі за замовчуванням | Лише **теги**                 | `body, a, h1 { … }`                      |
| **Layout** | Великі секції сторінки               | id або класи з префіксом `l-` | `.l-header`, `.l-sidebar`                |
| **Module** | Перевикористовувані компоненти       | Класи (без id)                | `.nav`, `.card`, `.login-form`           |
| **State**  | Стани модулів чи лейаутів            | Префікси `is-`, `has-`        | `.is-active`, `.is-hidden`, `.has-error` |
| **Theme**  | Тема оформлення                      | Окремі файли                  | `theme-dark.css`                         |

```html

<header class="l-header">
    <nav class="nav">
        <a class="nav__link is-active" href="#">Головна</a>
    </nav>
</header>
```

| ✅ Переваги                                | ❌ Недоліки                                   |
|-------------------------------------------|----------------------------------------------|
| Гнучка, підлаштовується під різні проєкти | Може бути складною для новачків              |
| Логічний поділ CSS на файли               | Дозволяє id і ланцюжки селекторів для станів |

> 💡 Префікси станів `is-` / `has-` з SMACSS широко використовують і разом із BEM. Зручне правило: `is-*` — для станів,
> які перемикає JavaScript (`el.classList.toggle('is-open')`), BEM-модифікатор — для варіантів, заданих у розмітці (
`button--primary`).
>
> Тему (Theme) сьогодні зазвичай реалізують через CSS-змінні: `[data-theme="dark"] { --bg: #111; }`.

## 5. ITCSS (Inverted Triangle CSS)

**ITCSS** (автор — Гаррі Робертс) — організовує стилі у вигляді **перевернутої піраміди**: від **загальних** стилів із *
*низькою специфічністю** до **конкретних** з **високою**.

```
 ▼ широке охоплення, низька специфічність
████████████████████████████████████  1. Settings   — змінні, кольори, шрифти  (не генерують CSS)
  ████████████████████████████████    2. Tools      — міксини, функції         (не генерують CSS)
    ████████████████████████████      3. Generic    — reset, normalize, box-sizing
      ████████████████████████        4. Elements   — h1, p, a (без класів)
        ████████████████████          5. Objects    — .o-container, .o-grid (каркас)
          ████████████████            6. Components — .card, .btn
            ████████████              7. Utilities  — .u-hidden, .text-center
 ▲ вузьке охоплення, висока специфічність (утиліти можуть мати !important)
```

Структура папок:

```
scss/
├── settings/   _colors.scss
├── tools/      _mixins.scss
├── generic/    _reset.scss
├── elements/   _typography.scss
├── objects/    _container.scss
├── components/ _card.scss
│               _button.scss
├── utilities/  _helpers.scss
└── main.scss
```

```scss
// style.scss — порядок імпорту = порядок шарів
@use 'settings/colors';
@use 'tools/mixins';
@use 'generic/reset';
@use 'elements/typography';
@use 'objects/container';
@use 'components/card';
@use 'components/button';
@use 'utilities/helpers';
```

**Головна ідея:** кожен наступний шар **лише доповнює** попередні, специфічність **тільки зростає** → кожне правило
перекриває попередні природним шляхом, без `!important`-воєн.

| ✅ Переваги                              | ❌ Недоліки                                            |
|-----------------------------------------|-------------------------------------------------------|
| Чудово керує стилями у великих проєктах | Складно налаштувати й підтримувати на початку         |
| Передбачуваний каскад                   | Потрібно розуміти, до якого шару віднести кожен стиль |

### Нативний аналог: каскадні шари `@layer`

```css
/* оголошуємо порядок шарів один раз */
@layer reset, base, components, utilities;

@layer components {
    #promo .card .title {
        color: navy;
    }

    /* (1,2,0) */
}

@layer utilities {
    .text-red {
        color: red;
    }

    /* (0,1,0) — але перемагає! */
}
```

Шари перевіряються в каскаді **раніше**, ніж специфічність: правило з пізніше оголошеного шару перемагає, навіть якщо
його селектор слабший. Стилі **поза** шарами перемагають усі шари. Підтримка — усі сучасні браузери (з 2022).

## 6. Atomic CSS

**«Одне правило — один стиль»**: кожен клас робить рівно **одну** річ.

```html

<div class="flex items-center justify-between p-4 bg-white rounded-lg shadow">
    <h3 class="text-lg font-bold text-gray-900">Pug</h3>
    <a class="px-4 py-2 bg-blue-500 text-white rounded hover:bg-blue-600 md:px-6">Більше</a>
</div>
```

```css
.flex {
    display: flex;
}

.p-4 {
    padding: 1rem;
}

.text-center {
    text-align: center;
}

.bg-blue {
    background: blue;
}
```

Найвідоміша сучасна реалізація — **[Tailwind CSS](https://tailwindcss.com/)**: він генерує **лише ті** утиліти, що
реально використані в HTML. Префікси `hover:`, `md:` — це псевдокласи та медіазапити прямо в назві класу.

Tailwind особливо популярний у React/Vue-проєктах: повторювана розмітка вже винесена в компоненти, тож «довгі» списки
класів пишуться один раз.

| ✅ Переваги                                      | ❌ Недоліки                           |
|-------------------------------------------------|--------------------------------------|
| Дуже швидка розробка, не треба вигадувати назви | HTML перевантажений класами          |
| CSS майже не росте з розміром проєкту           | Важче читати й підтримувати розмітку |
| Немає конфліктів і проблем зі специфічністю     | Потрібно вивчити «словник» утиліт    |

## 7. Порівняння методологій

| Методологія | Головна ідея                  | Що регулює                           | Ключове слово                          |
|-------------|-------------------------------|--------------------------------------|----------------------------------------|
| **BEM**     | Незалежні блоки               | Іменування класів                    | `block__element--modifier`             |
| **OOCSS**   | Перевикористовувані об'єкти   | Відокремлення структури й оформлення | Structure vs skin                      |
| **SMACSS**  | 5 категорій стилів            | Організацію файлів + префікси        | Base / Layout / Module / State / Theme |
| **ITCSS**   | Від загального до конкретного | Порядок шарів і специфічність        | Перевернута піраміда                   |
| **Atomic**  | Один клас — одна властивість  | Утилітарні класи                     | `.p-4`, `.flex`                        |

### Загальні переваги та недоліки методологій

| ✅ Переваги              | ❌ Недоліки                               |
|-------------------------|------------------------------------------|
| Краща організація коду  | Збільшення кількості класів              |
| Масштабованість         | Потрібен час на навчання й адаптацію     |
| Легке керування стилями | Деякі методології складні у використанні |
| Менше конфліктів стилів |                                          |

### 🧭 Що обрати?

| Тип проєкту                | Рекомендація                                                                  |
|----------------------------|-------------------------------------------------------------------------------|
| Навчальний проєкт, лендинг | **BEM** + проста структура: settings → base → layout → components → utilities |
| Великий сайт, команда      | **ITCSS** (або `@layer`) + **BEM** + стани `is-*`                             |
| React / Vue / Angular      | **CSS Modules**, scoped-стилі або **Tailwind** — ізоляцію дає інструмент      |
| **Наш курс**               | **BEM обов'язково** + SCSS-partials за шарами ITCSS                           |

**CSS Modules** — збирач автоматично перейменовує класи (`.title` → `.Card_title__x7a2`), тому конфлікти неможливі без
жодних домовленостей.

## 8. Сучасний CSS і методології

Нові можливості CSS не скасовують методології, а **допомагають** їм:

| Можливість                            | Приклад                               | Що дає                                                     |
|---------------------------------------|---------------------------------------|------------------------------------------------------------|
| **Нативна вкладеність** (CSS Nesting) | `.card { &:hover { … } }`             | Як у SCSS, але без компіляції                              |
| **`@layer`**                          | `@layer base, components, utilities;` | Порядок шарів замість війни специфічності (ідея ITCSS)     |
| **`@scope`**                          | `@scope (.card) { img { … } }`        | Обмежує стилі піддеревом DOM                               |
| **Custom properties**                 | `.button--danger { --btn-bg: red; }`  | Теми й модифікатори через змінні                           |
| **`:where()`**                        | `:where(ul, ol) { padding: 0; }`      | Селектор з нульовою специфічністю — зручно для base-стилів |

> ⚠️ Склеювання назв `&__title` працює **лише в SCSS**. У нативній вкладеності `&` — це посилання на селектор, а не
> рядок, тому BEM-класи в чистому CSS пишемо повністю.

Інструменти змінюються, а **принципи** — низька специфічність, незалежні компоненти, передбачуваний порядок — лишаються.

## 9. Workflow верстки: від макета до продакшну

```
1. Аналіз макета → 2. Середовище → 3. HTML-структура → 4. Reset + змінні
      → 5. Глобальні стилі → 6. Компоненти → 7. Контент → 8. Тестування → 9. Оптимізація
```

### 1. Підготовка та планування

- **Аналіз макета** (Figma): визначте блоки, компоненти, що повторюються, кольори, шрифти, відступи, breakpoints.
- **Планування:** продумайте HTML-структуру та CSS-методологію.
- **Вибір інструментів:** препроцесори (Sass), фреймворки (Bootstrap, Tailwind), збирачі (Vite).

> 💡 Роздрукуйте або зробіть скріншот макета й **обведіть фломастером блоки** з BEM-назвами — так ви побачите структуру
> ще до першого рядка коду.

### 2. Налаштування середовища

- структура папок: `css/` (`scss/`), `js/`, `images/`, `fonts/`;
- базові файли: `index.html`, `main.css`, `reset.css` / `normalize.css`;
- **Git**-репозиторій з першого дня;
- збирач (Vite / Gulp) — див. лекцію 13.

### 3. Базова HTML-структура

- семантична розмітка: `header`, `main`, `section`, `footer`…;
- BEM-класи одразу в розмітці;
- розбиття на компоненти (окремі Pug-файли / partials);
- HTML пишемо **повністю до** CSS — так класи виходять логічними, а не «підігнаними під стилі».

### 4. Базові стилі та скидання

- `reset.css` або `normalize.css`;
- змінні (`settings.scss` або CSS custom properties): кольори, шрифти, відступи, breakpoints.

### 5. Глобальні стилі

- `body`, `h1–h6`, `p`, `a`, `button`;
- контейнери: `.container`, `.wrapper` — вирівнювання й центрування.

### 6. Компоненти та модулі

- починайте з глобальних: **header, footer, навігація**;
- далі компоненти: картки, кнопки, форми — з обраною методологією;
- медіазапити додавайте **одразу** для кожного компонента, а не «в кінці»:

```scss
.card {
    display: grid;
    gap: 12px;

    @media (min-width: 768px) {
        grid-template-columns: 1fr 2fr;
    }
}
```

> 💡 Кроки 4 → 5 → 6 — це рух згори вниз по піраміді ITCSS: settings/generic → elements/objects → components.

### 7. Контентні блоки

- основні блоки з текстом, зображеннями, відео.

### 8. Тестування та налагодження

- різні браузери: Chrome, Firefox, **Safari**, Edge;
- різні екрани: мобільні, планшети, десктопи (DevTools → Device Mode);
- клавіатурна навігація, валідатор W3C.

### 9. Оптимізація та фінальні правки

- стиснення зображень (WebP/AVIF);
- перевірка швидкості: **Lighthouse**, PageSpeed Insights;
- мініфікація CSS, видалення невикористаних стилів.

### ✅ Чек-лист перед здачею проєкту

- [ ] Валідний HTML (0 помилок на validator.w3.org)
- [ ] Семантичні теги, один `<h1>`, `alt` у всіх зображень
- [ ] Класи за єдиною методологією (BEM)
- [ ] Немає стилів за id та `!important` (крім обґрунтованих утиліт)
- [ ] `box-sizing: border-box` для всіх елементів
- [ ] Адаптивність від 320px до 1920px без горизонтальної прокрутки
- [ ] Працює в Chrome, Firefox, Safari
- [ ] Видимий `:focus` та навігація з клавіатури
- [ ] Зображення оптимізовані, `loading="lazy"` нижче першого екрана
- [ ] Lighthouse ≥ 90 за всіма показниками
