Принципи функціонування
всесвітньої павутини (WWW)

Всесвітня павутина (WWW) - це система взаємопов'язаних документів і ресурсів, пов'язаних гіперпосиланнями та URL-адресами. Це мережа вебсерверів, що хостять вебсайти, вебзастосунки до яких можна отримати доступ через інтернет

World Wide Web (WWW) - не синонім Інтернету. Інтернет - фізична й логічна інфраструктура мереж (TCP - Transmission Control Protocol/IP - Internet Protocol). Веб - один із сервісів, що працює поверх неї, разом з поштою, FTP (File Transfer Protocol), DNS (Domain Name System), WebSocket тощо.

Принципи функціонування
всесвітньої павутини (WWW)

Веб з'явився 1989–1991 рр. завдяки Тіму Бернерсу-Лі (CERN - Conseil Européen pour la Recherche Nucléaire/Європейська організація з ядерних досліджень).

  • 1990 рік - за допомогою колеги Роберта Кайо, Тім Бернерс-Лі розробив протокол HTTP, систему адресації URI та мову HTML.
  • 20 грудня 1990 року - запрацював перший у світі внутрішній вебсайт info.cern.ch.
  • 30 квітня 1993 року - CERN офіційно оголосив, що технологія World Wide Web стає безкоштовною та відкритою для всіх.

Веб базується на трьох китах:

  • URI/URL (Uniform Resource Identifier/Uniform Resource Locator) - унікальна адреса ресурсу (https://example.com/products/123)
  • HTTP (Hypertext Transfer Protocol) - протокол обміну цими ресурсами
  • HTML (HyperText Markup Language) - формат документа з гіперпосиланнями

Ключова інновація - саме гіперпосилання, тобто документ перестає бути ізольованим файлом і стає вузлом глобального графа.

Принципи функціонування

URI (Uniform Resource Identifier) - це загальне поняття, тобто будь-який рядок, що ідентифікує ресурс (за місцем, іменем або обома способами відразу). URI — специфікація RFC (Request for Comments - це пронумерований офіційний документ, який визначає технічні стандарти, протоколи та правила роботи мережі Інтернет) 3986.

URI поділяється на два підтипи за способом ідентифікації:

  • URL (Uniform Resource Locator) - ідентифікує ресурс за його місцезнаходженням (вказує, де знайти і як до нього дістатись - протокол, хост, шлях). URL: https://example.com/books/978-3-16-148410-0.pdf → каже: "цей ресурс лежить ось за цією адресою"
  • URN (Uniform Resource Name) - ідентифікує ресурс за іменем, незалежно від того, де він фізично знаходиться і чи існує взагалі в мережі. URN: urn:isbn:978-3-16-148410-0 → каже: "це книга з таким ISBN", але НЕ каже, де саме її знайти в мережі.

Поняття які використовуються в WEB

  • Ваше інтернет-з'єднання - дає змогу надсилати та приймати дані мережею. Воно подібне до вулиці між будинком і магазином.
  • TCP/IP - Протокол Управління Передачею та Інтернет Протокол є комунікаційними протоколами, які визначають, яким чином дані повинні передаватися мережею. Вони як транспортні засоби, які дають змогу зробити замовлення, піти в магазин і купити ваші товари. У нашому прикладі, це як автомобіль або велосипед (або власні ноги).
  • DNS (Domain Name System) - Система Доменних Імен нагадує записник для вебсайтів. Коли ви вводите вебадресу у своєму браузері, браузер звертається до DNS, щоб знайти реальну адресу вебсайту, перш ніж він зможе її отримати. Браузеру необхідно з'ясувати, на якому сервері живе сайт, тому він може надсилати HTTP-повідомлення в потрібне місце.

Що ж насправді відбувається?

Коли ви вводите вебадресу у свій браузер (для нашої аналогії - відвідуєте магазин):

  1. Браузер звертається до DNS сервера і знаходить реальну адресу сервера, на якому «живе» сайт (Ви знаходите адресу магазину).
  2. Браузер надсилає HTTP-запит до сервера, запитуючи його надіслати копію сайту для клієнта (Ви йдете в магазин і замовляєте товар). Це повідомлення і всі інші дані, що передаються між клієнтом і сервером, передаються по інтернет-з'єднанню з використанням протоколу TCP/IP.

DNS (Domain Name System)

Реальні вебадреси - незручні, незабутні рядки, які ви вводите в адресний рядок, щоб знайти ваші улюблені вебсайти. Ці рядки складаються з чисел, наприклад: 63.245.215.20.

Такий набір чисел називається IP-адресою і являє собою унікальне місце розташування в Інтернеті. Утім, його не дуже легко запам'ятати, правда? Ось чому винайшли DNS. Це спеціальні сервери, які пов'язують вебадресу, яку ви вводите в браузері (наприклад, «mozilla.org»), з реальною IP-адресою сайту.

Сайти можна знайти безпосередньо через їхні IP-адреси. Ви можете знайти IP-адресу вебсайту, ввівши його домен в інструмент, як IP Checker.

Як працює DNS-запит? (Ілюстрація, як працює DNS)

  1. Набираємо chnu.edu.ua в адресному рядку браузера.
  2. Браузер запитає ваш комп'ютер, чи знає він уже, якій IP-адресі відповідає цей домен (використовуючи локальний DNS-кеш). Якщо ім'я є в кеші, воно транслюється в IP-адресу і браузер прямує до необхідного сервера. І все.
  3. Якщо ж ваш комп'ютер не знає, яка IP-адреса відповідає доменному імені chnu.edu.ua, він запитує DNS-сервер, чиє завдання - повідомити вашому комп'ютеру, яка IP-адреса відповідає запитаному доменному імені.
  4. Тепер ваш комп'ютер знає відповідність і може взаємодіяти із сервером.

Архітектура клієнт-серверної взаємодії за протоколом HTTP/HTTPS

Архітектура - це опис системи на найвищому рівні.

Тобто під час опису архітектури ми не вдаємося в подробиці кожного конкретного модуля, а скоріше описуємо їхню взаємодію між собою, «фіксуємо домовленості» поведінки кожного з них.

Клієнт-серверна архітектура описує, як взаємодіють між собою клієнт (у нашому випадку Frontend) і сервер (Backend).

Запити (request) й відповіді (response)

Як ми пам'ятаємо, клієнт-серверна архітектура будується на запитах і відповідях. Розберемося, що використовує браузер, щоб послати на сервер якийсь запит.

На рівні застосунку ми використовуємо вбудоване браузерне API, а саме - fetch(). Це глобальний метод для надсилання запитів.

HTTP-методи

Основні HTTP-методи: GET, POST, PATCH, PUT, DELETE.

Вони вказують, яку дію ми хочемо виконати. Метод POST - повідомить серверу, що ми хочемо створити новий ресурс і зберегти в нього вміст body.

Якби ми хотіли отримати якийсь ресурс, ми б використовували GET. Для редагування - PATCH, для заміни - PUT, а для видалення - DELETE.

HTTP-метод використовується в протоколі HTTP - протоколі передавання даних, яким за замовчуванням користуються браузери під час спілкування із сервером.

Протокол HTTP (Hyper Text Transfer Protocol)

Протокол — це певний набір правил або угод, який визначає, як відбуватиметься обмін даними. HTTP було розроблено як протокол обміну даними між вебсервером і веббраузером. Це протокол прикладного рівня моделі OSI, який використовується для передавання між клієнтом і сервером файлів HTML, CSS, JS, API, картинок, аудіо, відео, введених користувачем даних та іншого. Клієнт (веб-браузер) надсилає серверу (веб-серверу) запити й отримує від нього відповіді. Сервер у рамках протоколу HTTP практично завжди займає пасивну позицію.

OSI (Open Systems Interconnection - опис принципів роботи протоколів мережевої взаємодії, специфікація яких закріплена в стандартах зв'язку і використовується для передавання даних у цифровому вигляді)

Протокол HTTP: як зрозуміти?

Є три головні об'єкти, які обмінюються повідомленнями:

  1. Клієнт (user agent) - програма, яка надсилає запити, отримує та обробляє відповіді від імені користувача на пристрої користувача, наприклад, браузер.
  2. Сервер (вебсервер) - програма, яка працює на сервері, приймає та обробляє запити від клієнта, а потім надсилає відповіді клієнту. Цією програмою є вебсервер (nginx, apache, nodejs, express).
  3. Проксі (проксі-сервер) - програма, яка працює на сервері, пропускає через себе запити й відповіді та виступає в ролі посередника між клієнтом і сервером.

Протокол HTTP: як зрозуміти?

На першому етапі клієнт встановлює з'єднання із сервером за допомогою протоколу транспортного рівня TCP (Transmission Control Protocol). Клієнт може перевикористовувати одне й те саме з'єднання для роботи із сервером або створювати його щоразу. Це залежить від завдання, конфігурації мережі та конкретних налаштувань обладнання. Після встановлення з'єднання клієнт надсилає HTTP-повідомлення з тілом і параметрами запиту. Сервер приймає це повідомлення і на підставі логіки роботи бекенда формує і відправляє HTTP-повідомлення відповіді.

Протокол HTTP: як зрозуміти?

Протокол HTTP не зберігає стан, тому кількість з'єднань не призводить до істотного ускладнення взаємодії між об'єктами системи. Однак існує поняття сесії, за допомогою якої можна передавати й зберігати необхідні дані, що належать до конкретного сеансу зв'язку. Дані сесії зберігаються на клієнті та на сервері. Наприклад, доступний ідентифікатор сесії, який дає змогу не проводити авторизацію клієнта під час кожного звернення до сервера.

Часто для зберігання даних про сесію використовують Cookie.

Протокол HTTP: проксі-сервери

Проксі-сервери здійснюють сервісні функції:

  • Кешувати дані запиту або відповіді для поліпшення продуктивності та зниження мережевого трафіку.
  • Фільтрувати дані. Наприклад, можна сканувати дані антивірусом або використовувати батьківський контроль.
  • Здійснювати балансування навантаження, розподіляючи запити між різними серверами.
  • Проводити аутентифікацію клієнтів для управління доступом до ресурсів.
  • Зберігати інформацію про запити клієнтів і відповіді сервера, реалізуючи таким чином логування.
  • Виявляти деякі типи атак на мережевий вузол (наприклад, визначення підозрілого трафіку або DDoS-атаки).

Протокол HTTP: формат повідомлення

HTTP-повідомлення являє собою звичайний текст. Структура повідомлення строго визначена:

  1. Стартовий рядок (Starting line);
  2. Заголовки (Headers), опис параметрів повідомлення, передають сервісну інформацію;
  3. Тіло повідомлення (Body), представляє дані в текстовому вигляді.
Тіло повідомлення - це опціональна частина повідомлення, яка може бути відсутня. Наприклад, для деяких GET-запитів (тобто запитів з боку клієнта, як метод отримання даних для якого обрано метод GET) або для всіх HEAD-запитів. Якщо тіло повідомлення присутнє, то це позначається заголовками Content-Length або Transfer-Encoding.

Протокол HTTP: Стартовий рядок (Starting line)

Стартовий рядок запиту містить інформацію про метод запиту, відносну адресу та версію протоколу у форматі Метод URI HTTP/Версія. Стартовий рядок відповіді містить версію протоколу, код і статус відповіді сервера у форматі HTTP/Версія Код Статус.

Коли браузер надсилає запит на відкриття головної сторінки сайту, стартовий рядок запиту буде таким: GET / HTTP/1.1

Якщо сторінка існує і до неї є доступ, то стартовий рядок відповіді буде таким: HTTP/1.1 200 OK

Протокол HTTP: Status Code

Код стану у відповіді сервера містить інформацію про результат обробки даних. Існує п'ять класів кодів станів (Status Code Registry, HTTP Status Codes Glossary):

  1. 1xx - обробка даних на сервері триває;
  2. 2xx - успішна обробка даних;
  3. 3xx - перенаправлення запитів;
  4. 4xx - помилка з вини клієнта;
  5. 5xx - помилка з вини сервера.
  • 200 OK у разі успішного опрацювання запиту.
  • 301 Moved Permanently якщо редірект використовується на постійній основі.
  • 307 Temporary Redirect якщо редірект використовується тимчасово.
  • 400 Bad Request якщо в запиті є синтаксична помилка.
  • 403 Forbidden якщо запит успішний, але сервер його не може виконати, оскільки користувач не має достатніх прав.
  • 404 Not Found якщо запитаного ресурсу не існує.
  • 500 Internal Server Error якщо робота програми на сервері видала помилку.

Протокол HTTP: Headers

Заголовки поділяються на чотири групи:

  1. Основні заголовки, які можуть включатися в будь-які повідомлення клієнта і сервера.
  2. Заголовки запиту, які використовуються тільки в повідомленнях клієнта.
  3. Заголовки відповіді, які використовуються тільки в повідомленнях сервера.
  4. Заголовки сутності, які описують дані в повідомленні.

У заголовках вказується різна необхідна для роботи вебсервера або клієнта інформація. Наприклад, є адреса домену, до якого звертається клієнт або інформація про авторизацію користувача. Також заголовки можуть містити інформацію про налаштування кешування на клієнті та сервері, формат переданих даних, мову, останню дату і час модифікації даних тощо.

Протокол HTTP: Body

Формат даних тіла повідомлення може бути декількох типів, які закріплені в специфікаціях HTTP-протоколу різних версій (HTTP/1.0 (стандарт RFC 1945), HTTP/1.1 (стандарт RFC 2616), HTTP/2 (чернетка стандарту), HTTP/3 (чернетка стандарту)). Найчастіше зустрічаються типи:

  • text/html.
  • application/json.
  • multipart/form-data.

REST (Representational State Transfer)

REST (Representational State Transfer) - стиль спілкування компонентів, за якого всі необхідні дані вказуються в параметрах запиту.

Відмітна особливість цього стилю - це стиль побудови адрес і вибір методу.

Наприклад, метод і адреса для створення користувача могли б виглядати так: POST /api/users
Для отримання конкретного користувача: GET /api/users/1 (Де 1 - це ID користувача.)
Для редагування даних про користувача: PATCH /api/users/1
Для видалення даних: DELETE /api/users/1

Еволюція стандартів консорціуму W3C

W3C (World Wide Web Consortium) заснований 1994 р. Бернерсом-Лі для узгодження стандартів між виробниками браузерів.

  1. 1991 — HTML 1.0 (~20 тегів)
  2. 1996 — CSS1 (відокремлення стилю від структури)
  3. 1997 — ECMAScript 1 (стандарт JS)
  4. 2008–2014 — HTML5 (семантика, canvas, video, робота без плагінів на кшталт Flash)
  5. 2015+ — ES6 (класи, модулі, стрілкові функції, let/const) і щорічні редакції ECMAScript; CSS3 модульно (Grid, Flexbox, Custom Properties)

Після HTML5 специфікація фактично стала "живим стандартом" (living standard) — розвивається WHATWG разом з W3C, без фіксованих.

Як працює вебзастосунок

Будь-який вебзастосунок, якщо він працює в браузері, працює на 3 основних технологіях: HTML, CSS і JS.

Усі застосунки, якими ви користуєтеся в браузері: Google Apps, YouTube, Moodle - зроблені за допомогою цих технологій.

Але будь-який складний застосунок - це не тільки картинка в браузері, це ще й дані, які користувачі використовують або створюють. Ці дані потрібно вміти зберігати, обробляти і виводити.

Як працює вебзастосунок

Зберіганням і обробкою даних зазвичай займається сервер або бекенд.

Бекенд (Backend) - область вебтехнологій, що працюють на сервері, а також внутрішня частина серверної системи, що займається обробкою даних.

А архітектура, в якій беруть участь сервер (Backend) і клієнт (браузер, Frontend) називається клієнт-серверною.

Клієнт

Клієнт звертається із запитами до сервера.

Запити можуть бути різні. Клієнт може попросити сервер віддати якісь дані або попросити їх якось підготувати перед віддачею. Або ж може попросити сервер зберегти щось, що передасть разом із запитом сам.

Роль клієнта для сервера в тому, щоб повідомити серверу, що потрібно зробити з даними, які зберігаються в базі, або з даними, які він передає.

Роль клієнта для користувача в тому, щоб представити дані в зручному вигляді та надати механізми для їх оновлення.

Сервер

Сервер приймає запити від клієнта.

Його роль у тому, щоб зберігати інформацію від клієнта в базі даних (БД), обробляти її та надавати до неї доступ за деякими правилами. Такі правила зазвичай називаються бізнес-логікою.

На сервері, крім спілкування з клієнтом, можуть запускатися якісь фонові завдання, наприклад, індексування інформації в базі даних для швидшого пошуку або запуск автоматичних email-розсилок.

БД - це сховище всієї користувацької та службової інформації. Її роль у тому, щоб забезпечувати швидкий і безперебійний доступ до цієї інформації та власне зберігання.

Технології для створення вебзастосунок

Розвиток вебзастосунків

На клієнт-серверній архітектурі побудована більша частина застосунків. Однак перші застосунки все ж трохи відрізнялися від нинішніх у деталях реалізації. Головною відмінністю було повне перезавантаження сторінки у відповідь на будь-яку дію.

Найперші вебзастосунки не сильно відрізнялися від звичайних сайтів.

По суті це і були сайти, тому що вся бізнес-логіка реалізовувалася на сервері. Клієнт лише показував результат у вигляді HTML-сторінок користувачеві і надсилав запити на інші сторінки.

Розвиток вебзастосунків

Банальний вибір сортування списку або таблиці вимагав перезавантаження сторінки. Зараз це виглядає не сучасно, але перші додатки працювали винятково таким чином просто тому, що в браузерах не було інструменту для альтернативного спілкування.

На початку нульових з'явився так званий «WEB 2.0», з яким прийшов AJAX.

AJAX

AJAX (Asynchronous JavaScript and XML) - спілкування між клієнтом і сервером без перезавантаження сторінки.

Коли ми говоримо, що якийсь застосунок використовує AJAX, ми маємо на увазі, що під час натискання, наприклад, на кнопку сортування списку або таблиці, сторінка не перезавантажиться, а сортування відбудеться ніби «на фоні».

Під час натискання браузер надішле запит на сервер, у якому повідомить, що йому необхідно відсортувати такий-то список за таким-то критерієм.

Сервер обробить запит, дістане потрібні дані, відсортує їх і надішле клієнту готовий шматок інтерфейсу, який клієнт уже вставить у документ.

Зауважте, що ми все ще не передаємо дані в чистому вигляді. Зараз на клієнті ми приймаємо шматок HTML-розмітки, який потім вбудовуємо в потрібне місце в документі.

Сучасні вебзастосунки

У сучасних застосунках між клієнтом і сервером спілкування будується саме на даних, а не на відрендерених шматках розмітки. Найчастіше для такого спілкування обирають JSON. Зараз більша частина додатків працює так:

  1. Клієнт робить первинний запит на сервер.
  2. Сервер відповідає HTML-сторінкою, іноді з набором якихось даних, впроваджених у вигляді JS-об'єкта в кінці сторінки.
    1. Сторінка може бути відмальована на сервері й тоді клієнту прийде готовий HTML.
    2. Або відтворенням займатиметься сам клієнт за допомогою якоїсь бібліотеки, наприклад, React, Vue, Angular. У цьому випадку від сервера приходить просто набір необхідних даних.

Сучасні вебзастосунки

  1. Користувач здійснює якусь дію, наприклад, просить відсортувати таблицю.
  2. Клієнт у відповідь на цю дію вирішує, який запит відправити на сервер, будує цей запит і відправляє його.
  3. Сервер приймає цей запит, обробляє його і відправляє на клієнт порцію нових даних.
  4. Клієнт приймає дані й перемальовує частину сторінки за ними сам. Тобто він уже не замінює один шматок розмітки іншим готовим, а малює розмітку сам.

Сучасні вебзастосунки

  • Переваги такого спілкування (коли передаються тільки дані) кілька:
  • Сервер і клієнт стають незалежними один від одного. Сервер може нічого не знати про побудову сторінок, йому достатньо лише вміти працювати з БД і обробляти дані (первинне відмальовування (рендер) може бути зроблене самим сервером за допомогою SSR - Server-Side Rendering). Способи генерації сторінок.
  • Кількість інформації, яку доводиться передавати й приймати, менша - а це зменшує обсяг трафіку. Логіка застосунку на сервері може бути простішою, тому він і клієнт стають менш залежними один від одного в плані формату даних.

JSON (JavaScript Object Notation)

JSON (JavaScript Object Notation) - один із найпопулярніших форматів даних. Він небагатослівний, зрозумілий і людині, і комп'ютеру, багато мов із ним уже вміють працювати. JSON wiki.

У вебі JSON, можна сказати, стандарт, тому що використовується як формат за замовчуванням у багатьох фреймворках.

Режими рендерингу браузера
(Quirks vs. Standards Mode)

Режим визначається наявністю й коректністю DOCTYPE на початку HTML-документа.

  • Quirks Mode — вмикається без DOCTYPE або із застарілим DOCTYPE. Імітує поведінку браузерів 1990-х: нестандартна box model (padding/border входять у ширину блока), непередбачувана поведінка між браузерами.
  • Standards Mode — вмикається через !DOCTYPE html. Точна відповідність специфікаціям, стандартна box model.

Сьогодні Quirks Mode — переважно "музейний" артефакт (виникає лише, якщо забути DOCTYPE), але сама ідея "браузер по-різному трактує один і той самий CSS залежно від контексту" - актуальна досі (hello reset css)

Життєвий цикл рендерингу вебсторінки (Critical Rendering Path)

П'ять кроків від коду до пікселів на екрані:

  • DOM - парсинг HTML → Document Object Model
  • CSSOM - парсинг CSS → CSS Object Model
  • Render Tree - об'єднання DOM+CSSOM, лише видимі вузли (елементи з display: none не потрапляють)
  • Layout (reflow) - обчислення точних розмірів і координат кожного елемента
  • Paint (repaint) - растеризація пікселів по шарах
  • Composite - накладання шарів і вивід на екран (часто через GPU)

Стек базових технологій: HTML, CSS, JavaScript

  • HTML - структура/семантика (скелет)
  • CSS - представлення/стиль (зовнішній вигляд)
  • JavaScript - поведінка/інтерактивність (логіка й дії)

Наш курс фокусується саме на HTML/CSS-шарі - статичній верстці й адаптивному дизайні. Але важливо з першої лекції розуміти межу: HTML і CSS декларативні (описують "що" і "як виглядає"), JS імперативний (описує "що робити"). Ця відмінність визначає весь подальший спосіб мислення при верстці інтерфейсів.
