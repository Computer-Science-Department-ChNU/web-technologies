## 1. Навіщо потрібні методології

**CSS-методологія** — набір правил і домовленостей щодо **іменування класів** та **організації файлів стилів**.

### Проблеми CSS без правил 😱

- **Глобальність:** будь-який клас діє на всю сторінку → стилі одного компонента «ламають» інший.
- **Війна специфічності:** `.header .menu li a` → `#nav .menu li a` → `!important` → ...
- **Страх видаляти:** «а раптом цей клас десь ще використовується?» → CSS лише росте.
- **Неочевидні зв'язки:** з HTML не зрозуміло, які стилі де лежать.

### Що дають методології

| Перевага | Пояснення |
|---|---|
| 🛡 Уникнення конфліктів | Стилі не перезаписують один одного |
| 📖 Читабельність | Структура зрозуміла з назви класу |
| ♻️ Повторне використання | Компоненти переносяться між сторінками й проєктами |
| 📈 Масштабованість | Нові компоненти додаються без страху щось зламати |

**Популярні методології:** BEM, SMACSS, ITCSS, OOCSS, Atomic CSS. Вони **не взаємовиключні** — їх часто поєднують (наприклад, ITCSS для структури файлів + BEM для іменування).

## 2. BEM (Block, Element, Modifier)

Найпопулярніша методологія іменування. Інтерфейс ділиться на **незалежні блоки**.

### Синтаксис

```
block
block__element
block--modifier
block__element--modifier
```

| Сутність | Що це | Питання, на яке відповідає назва | Приклади |
|---|---|---|---|
| **Block** (блок) | Незалежний компонент, що має сенс сам по собі | **«Що це?»** | `header`, `menu`, `card`, `button`, `search-form` |
| **Element** (елемент) | Складова частина блоку, не існує окремо від нього | **«Що це?»** | `menu__item`, `card__title`, `search-form__input` |
| **Modifier** (модифікатор) | Стан, вигляд або поведінка | **«Який? / Як поводиться?»** | `button--disabled`, `menu__item--active`, `card--featured` |

### Приклад

```html
<article class="card card--featured">
  <img class="card__img" src="pug.png" alt="Pug">
  <h3 class="card__title">Pug</h3>
  <p class="card__text">Шаблонізатор для HTML</p>
  <a class="card__btn button button--primary" href="#">Детальніше</a>
</article>
```

```css
.card { padding: 16px; border-radius: 12px; }
.card--featured { border: 2px solid gold; }
.card__img { width: 100%; }
.card__title { font-size: 1.25rem; }
```

### Правила BEM

- ✅ Назви — за **змістом**, а не за виглядом: `button--danger` ✅, `button--red` ❌, `big-block` ❌.
- ✅ Стилізуємо **лише через класи** (не теги, не id).
- ✅ Специфічність усіх селекторів однакова (0,0,1,0) → **жодних воєн специфічності**.
- ❌ **Не** відображайте вкладеність DOM у назві: `card__body__title` ❌ → `card__title` ✅. Елемент належить **блоку**, а не іншому елементу.
- ✅ Модифікатор **завжди йде разом** з основним класом: `class="button button--primary"`, а не лише `button--primary`.
- ✅ Один HTML-вузол може бути одночасно **елементом** одного блоку і **блоком** сам по собі (**міксування**): `class="card__btn button"`.

### BEM + SCSS = ❤️

```scss
.card {
  padding: 16px;

  &__title { font-size: 1.25rem; }
  &__img   { width: 100%; }
  &--featured { border: 2px solid gold; }
}
```

| ✅ Переваги | ❌ Недоліки |
|---|---|
| Ідеально для компонентного підходу | Довгі назви класів |
| Зрозуміла структура з першого погляду на HTML | Потрібна дисципліна команди |
| Плоска специфічність | Спочатку здається «багатослівним» |

## 3. SMACSS

**SMACSS** (Scalable and Modular Architecture for CSS) — ділить стилі на **5 категорій**:

| Категорія | Що містить | Як стилізується | Приклад |
|---|---|---|---|
| **Base** | Нормалізація, стилі за замовчуванням | Лише **теги** | `body, a, h1 { … }` |
| **Layout** | Великі секції сторінки | id або класи з префіксом `l-` | `.l-header`, `.l-sidebar` |
| **Module** | Перевикористовувані компоненти | Класи (без id) | `.nav`, `.card`, `.login-form` |
| **State** | Стани модулів чи лейаутів | Префікси `is-`, `has-` | `.is-active`, `.is-hidden`, `.has-error` |
| **Theme** | Тема оформлення | Окремі файли | `theme-dark.css` |

```html
<header class="l-header">
  <nav class="nav">
    <a class="nav__link is-active" href="#">Головна</a>
  </nav>
</header>
```

| ✅ Переваги | ❌ Недоліки |
|---|---|
| Гнучка, підлаштовується під різні проєкти | Може бути складною для новачків |
| Логічний поділ CSS на файли | Дозволяє id і ланцюжки селекторів для станів |

> 💡 Префікси станів `is-` / `has-` з SMACSS широко використовують і разом із BEM.

## 4. ITCSS (Inverted Triangle CSS)

**ITCSS** (автор — Гаррі Робертс) — організовує стилі у вигляді **перевернутої піраміди**: від **загальних** стилів із **низькою специфічністю** до **конкретних** з **високою**.

```
 ▼ широке охоплення, низька специфічність
┌───────────────────────────────────────────┐
│ 1. Settings   — змінні, кольори, шрифти   │  (не генерують CSS)
├───────────────────────────────────────────┤
 │ 2. Tools     — міксини, функції        │    (не генерують CSS)
 ├─────────────────────────────────────────┤
  │ 3. Generic  — reset, normalize,      │
  │              box-sizing             │
  ├─────────────────────────────────────┤
   │ 4. Elements — h1, p, a (без класів)│
   ├───────────────────────────────────┤
    │ 5. Objects — .o-container,      │
    │              .o-grid (каркас)   │
    ├────────────────────────────────┤
     │ 6. Components — .card, .btn  │
     ├─────────────────────────────┤
      │ 7. Utilities — .u-hidden, │
      │    .text-center          │
      └─────────────────────────┘
 ▲ вузьке охоплення, висока специфічність (можуть мати !important)
```

```scss
// style.scss — порядок імпорту = порядок шарів
@use 'settings/colors';
@use 'tools/mixins';
@use 'generic/reset';
@use 'elements/typography';
@use 'objects/container';
@use 'components/card';
@use 'components/button';
@use 'utilities/helpers';
```

**Головна ідея:** кожен наступний шар **лише доповнює** попередні, специфічність **тільки зростає** → кожне правило перекриває попередні природним шляхом, без `!important`-воєн.

| ✅ Переваги | ❌ Недоліки |
|---|---|
| Чудово керує стилями у великих проєктах | Складно налаштувати й підтримувати на початку |
| Передбачуваний каскад | Потрібно розуміти, до якого шару віднести кожен стиль |

> 💡 Сучасний CSS має вбудований аналог цієї ідеї — **каскадні шари** `@layer`:
>
> ```css
> @layer reset, base, components, utilities;
> @layer components { .card { … } }
> ```

## 5. OOCSS (Object-Oriented CSS)

Запропонована **Ніколь Салліван** (Nicole Sullivan, 2008). Ідея з ООП: створювати перевикористовувані CSS-**«об'єкти»**.

### Два принципи

**1. Separate structure and skin — відокремлюйте структуру від оформлення**

```css
/* ❌ Без OOCSS: усе змішано, дублювання */
.btn-login  { padding: 8px 16px; border-radius: 4px; background: blue; }
.btn-delete { padding: 8px 16px; border-radius: 4px; background: red; }

/* ✅ OOCSS: структура окремо, «шкірки» окремо */
.btn        { padding: 8px 16px; border-radius: 4px; } /* structure */
.skin-blue  { background: blue; }                      /* skin */
.skin-red   { background: red; }
```

```html
<button class="btn skin-blue">Увійти</button>
<button class="btn skin-red">Видалити</button>
```

**2. Separate container and content — відокремлюйте вміст від контейнера**

```css
/* ❌ Залежність від місця: заголовок виглядає інакше в сайдбарі */
.sidebar h3 { font-size: 18px; }

/* ✅ Об'єкт виглядає однаково будь-де */
.heading-small { font-size: 18px; }
```

| ✅ Переваги | ❌ Недоліки |
|---|---|
| Гнучкі, перевикористовувані компоненти | Багато класів в HTML |
| Менше дублювання CSS | Відсутність строгих правил іменування → «зоопарк» класів |

## 6. Atomic CSS

**«Одне правило — один стиль»**: кожен клас робить рівно **одну** річ.

```html
<div class="flex items-center justify-between p-4 bg-white rounded-lg shadow">
  <h3 class="text-lg font-bold text-gray-900">Pug</h3>
  <a class="px-4 py-2 bg-blue-500 text-white rounded hover:bg-blue-600">Більше</a>
</div>
```

```css
.flex { display: flex; }
.p-4 { padding: 1rem; }
.text-center { text-align: center; }
.bg-blue { background: blue; }
```

Найвідоміша сучасна реалізація — **[Tailwind CSS](https://tailwindcss.com/)**: він генерує **лише ті** утиліти, що реально використані в HTML.

| ✅ Переваги | ❌ Недоліки |
|---|---|
| Дуже швидка розробка, не треба вигадувати назви | HTML перевантажений класами |
| CSS майже не росте з розміром проєкту | Важче читати й підтримувати розмітку |
| Немає конфліктів і проблем зі специфічністю | Потрібно вивчити «словник» утиліт |

## 7. Порівняння методологій

| Методологія | Головна ідея | Що регулює | Ключове слово |
|---|---|---|---|
| **BEM** | Незалежні блоки | Іменування класів | `block__element--modifier` |
| **SMACSS** | 5 категорій стилів | Організацію файлів + префікси | Base / Layout / Module / State / Theme |
| **ITCSS** | Від загального до конкретного | Порядок шарів і специфічність | Перевернута піраміда |
| **OOCSS** | Перевикористовувані об'єкти | Відокремлення структури й оформлення | Structure vs skin |
| **Atomic** | Один клас — одна властивість | Утилітарні класи | `.p-4`, `.flex` |

### Загальні переваги та недоліки методологій

| ✅ Переваги | ❌ Недоліки |
|---|---|
| Краща організація коду | Збільшення кількості класів |
| Масштабованість | Потрібен час на навчання й адаптацію |
| Легке керування стилями | Деякі методології складні у використанні |
| Менше конфліктів стилів | |

> 🧭 **Що обрати студенту?** Почніть із **BEM** для іменування + структура файлів у дусі **ITCSS/SMACSS** (settings → base → layout → components → utilities). Це покриває 90% задач і поширено в реальних командах.

## 8. Workflow верстки: від макета до продакшну

```
1. Аналіз макета → 2. Середовище → 3. HTML-структура → 4. Reset + змінні
      → 5. Глобальні стилі → 6. Компоненти → 7. Контент → 8. Тестування → 9. Оптимізація
```

### 1. Підготовка та планування

- **Аналіз макета** (Figma): визначте блоки, компоненти, що повторюються, кольори, шрифти, відступи, breakpoints.
- **Планування:** продумайте HTML-структуру та CSS-методологію.
- **Вибір інструментів:** препроцесори (Sass), фреймворки (Bootstrap, Tailwind), збирачі (Vite).

> 💡 Роздрукуйте або зробіть скріншот макета й **обведіть фломастером блоки** з BEM-назвами — так ви побачите структуру ще до першого рядка коду.

### 2. Налаштування середовища

- структура папок: `css/` (`scss/`), `js/`, `images/`, `fonts/`;
- базові файли: `index.html`, `main.css`, `reset.css` / `normalize.css`;
- **Git**-репозиторій з першого дня.

### 3. Базова HTML-структура

- семантична розмітка: `header`, `main`, `section`, `footer`…;
- розбиття на компоненти (окремі Pug-файли / partials).

### 4. Базові стилі та скидання

- `reset.css` або `normalize.css`;
- змінні (`settings.scss` або CSS custom properties): кольори, шрифти, відступи, breakpoints.

### 5. Глобальні стилі

- `body`, `h1–h6`, `p`, `a`, `button`;
- контейнери: `.container`, `.wrapper` — вирівнювання й центрування.

### 6. Компоненти та модулі

- починайте з глобальних: **header, footer, навігація**;
- далі компоненти: картки, кнопки, форми — з обраною методологією;
- медіазапити додавайте **одразу** для кожного компонента, а не «в кінці».

### 7. Контентні блоки

- основні блоки з текстом, зображеннями, відео.

### 8. Тестування та налагодження

- різні браузери: Chrome, Firefox, **Safari**, Edge;
- різні екрани: мобільні, планшети, десктопи;
- клавіатурна навігація, валідатор W3C.

### 9. Оптимізація та фінальні правки

- стиснення зображень (WebP/AVIF);
- перевірка швидкості: **Lighthouse**, PageSpeed Insights;
- мініфікація CSS, видалення невикористаних стилів.

### ✅ Чек-лист перед здачею проєкту

- [ ] Валідний HTML (0 помилок на validator.w3.org)
- [ ] Семантичні теги, один `<h1>`, `alt` у всіх зображень
- [ ] Класи за єдиною методологією (BEM)
- [ ] Немає стилів за id та `!important` (крім обґрунтованих утиліт)
- [ ] `box-sizing: border-box` для всіх елементів
- [ ] Адаптивність від 320px до 1920px без горизонтальної прокрутки
- [ ] Працює в Chrome, Firefox, Safari
- [ ] Видимий `:focus` та навігація з клавіатури
- [ ] Зображення оптимізовані, `loading="lazy"` нижче першого екрана
- [ ] Lighthouse ≥ 90 за всіма показниками
